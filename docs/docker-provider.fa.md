# مشاهدهٔ Docker

[English](docker-provider.md)

نامزد مرحلهٔ ۵ از SDK رسمی `github.com/moby/moby/client` نسخهٔ `v0.6.2`
و `github.com/moby/moby/api` نسخهٔ `v1.56.1` استفاده می‌کند. نسخهٔ دوم، نسخهٔ
ماژول است؛ بیشینهٔ نسخهٔ HTTP برابر `1.56` و کمینهٔ کلاینت `1.40` است.
ساختارهای SDK داخل آداپتور می‌مانند. متغیرهای عمومی `DOCKER_HOST`،
`DOCKER_API_VERSION` و تنظیم TLS عمومی Docker خوانده نمی‌شوند.
[مرجع SDK](https://pkg.go.dev/github.com/moby/moby/client@v0.6.2).

تست‌های محلی با دادهٔ ساختگی، تنظیم و اتصال اجزا پاس شده‌اند. در ۲۰۲۶-۱۰-۱۷
تست واقعی mTLS محدود روی Engine لینوکس `29.1.3` با API توافق‌شدهٔ `1.52` و
Go `1.26.5` در ۱۲۸٫۰۱ ثانیه پاس شد. کشف، آمار زنده، گزارش و رویداد تاریخی،
احراز کلاینت و رد مسیرهای ممنوع پاس شدند. پس از پاک‌سازی، containerها، شبکه،
volume و تصویر اختصاصی همان تست باقی نماندند. نتیجهٔ اجرای دوردست کار مستقل
CI تا ثبت در [سند شواهد](implementation-plan.md) در انتظار است. سکوی دیگر یا
daemon اپراتور به سنجش جدا نیاز دارد.

## انتخاب پروفایل اپراتور

Docker پیش‌فرض خاموش است. مدیر احرازشده فقط منبع از پیش ثبت‌شده را فعال می‌کند؛
مرورگر نشانی، مسیر میزبان، گواهی یا نام متغیر محیطی تعیین نمی‌کند. اعتبارنامه
در مرورگر یا پایگاه داده ذخیره نمی‌شود.

| پروفایل | کاربرد | تنظیم لازم |
| --- | --- | --- |
| `docker_socket_dev` | توسعهٔ صریح با شنونده و مبدأ عمومی loopback | `STACKPLORE_DOCKER_ENABLED=true`؛ مسیر مطلق اختیاری `STACKPLORE_DOCKER_SOCKET_PATH` |
| `docker_restricted_proxy` | مشاهده از پروکسی مجوزدهی HTTPS ثابت | فعال‌کردن Docker، انتخاب `STACKPLORE_DOCKER_ACCESS_PROFILE=docker_restricted_proxy` و چهار مرجع زیر |

چهار مرجع عبارت‌اند از `STACKPLORE_DOCKER_PROXY_ORIGIN`،
`STACKPLORE_DOCKER_PROXY_CA_FILE`، `STACKPLORE_DOCKER_PROXY_CERT_FILE` و
`STACKPLORE_DOCKER_PROXY_KEY_FILE`: یک مبدأ HTTPS و سه مسیر مطلق فایل نصب‌شده.
`STACKPLORE_DOCKER_ENABLED=true` جدا لازم است. مبدأ نباید نام کاربری، گذرواژه،
مسیر، پرس‌وجو یا fragment داشته باشد. خواندن هر فایل CA، گواهی و کلید خصوصی
حداکثر یک MiB است. فایل باید عادی باشد؛ پیوند projected فقط داخل همان دایرکتوری
انتخاب‌شده پذیرفته می‌شود. خروج پیوند از محدوده، دایرکتوری، فایل بزرگ، تغییر مسیر
HTTP، پروکسی محیطی و TLS بدون تأیید رد می‌شوند.

سوکت مستقیم daemon اختیار گستردهٔ میزبان می‌دهد و فقط برای توسعهٔ loopback مجاز
است. نصب سوکت با حالت فقط‌خواندنی، درخواست‌های daemon را فقط‌خواندنی نمی‌کند.
در تولید سوکت را داخل API نصب نکنید. پروکسی مشاهده هیچ اختیار restart یا نوشتن
نمی‌دهد و پرچم نوشتن آن رد می‌شود. عملیات محافظت‌شده مرحلهٔ تحویل جدا دارد.

## آماده‌سازی Compose محدود

مراحل [نصب Compose و نخستین مدیر](operations/deployment.md) را انجام دهید.
[لایهٔ اختیاری Compose](../compose.docker.yaml) فقط
[سیاست بازبینی‌شدهٔ HAProxy](../deploy/docker-proxy/haproxy.cfg) و شبکهٔ خصوصی
مشاهده را اضافه می‌کند. تصویر پروکسی با digest ثابت است. شنوندهٔ پروکسی هیچ
درگاه منتشرشدهٔ میزبان ندارد؛ فقط پروکسی سوکت انتخاب‌شدهٔ اپراتور را می‌گیرد.

1. از PKI اپراتور گواهی سرور با DNS SAN شامل `docker-proxy` و هویت کلاینت جدا
   برای مشاهدهٔ همان daemon بگیرید. کاربرد server-auth و client-auth متناسب
   باشد. کلید خصوصی سرور را برای کلاینت تکرار نکنید.
2. دایرکتوری خصوصی سرور شامل `server.pem` با گواهی، زنجیره و کلید سرور، و
   `ca.pem` با صادرکنندگان مورد اعتماد کلاینت بسازید. پروکسی با UID/GID برابر
   65532 اجرا می‌شود. دایرکتوری و فایل‌های خصوصی فقط برای همان هویت قابل خواندن
   باشند. پروکسی قابلیت افزوده ندارد، فایل‌سیستم فقط‌خواندنی و
   `no-new-privileges` دارد.
3. دایرکتوری جداگانهٔ کلاینت شامل `ca.pem` با صادرکنندگان سرور، `client.pem`
   با زنجیرهٔ کلاینت و `client-key.pem` آماده کنید. فقط UID برابر 10001 برنامه
   دسترسی خواندن لازم را داشته باشد. نصب این دایرکتوری فقط‌خواندنی است. API
   کلید سرور و سوکت daemon را نمی‌گیرد.
4. در محیط خصوصی اپراتور یا فایل محیط Compose این نام‌های مخصوص Compose را
   تنظیم کنید: `DOCKER_PROXY_SERVER_DIRECTORY`،
   `DOCKER_PROXY_CLIENT_DIRECTORY` و `DOCKER_SOCKET_GID` را تنظیم
   کنید. مقدار آخر، شناسهٔ عددی گروه مالک سوکت انتخاب‌شدهٔ daemon است؛ سوکت از
   پیش مجوز خواندن و نوشتن همان گروه را داشته باشد. این گروه تکمیلی بدون root
   یا تغییر مجوز سوکت، دسترسی لازم را می‌دهد. در لینوکس با
   `stat -c '%g' /var/run/docker.sock` گروه را ببینید؛ مسیر واقعی تنظیم‌شده را
   به‌کار ببرید. در صورت نیاز
   `DOCKER_SOCKET_PATH` با پیش‌فرض `/var/run/docker.sock`.
   این نام‌ها ورودی جای‌گذاری Compose هستند و سرور مستقیم آن‌ها را نمی‌پذیرد.
5. مدل ترکیبی را بررسی و سپس اجرا کنید:

```sh
docker compose --env-file .env -f compose.yaml -f compose.docker.yaml config --quiet
docker compose --env-file .env -f compose.yaml -f compose.docker.yaml up --build -d
```

آمادگی API، وضعیت واقعی قابلیت منبع Docker و موجودی، گزارش و سنجهٔ یک container
مشخص را بررسی کنید. نبود نصب سوکت در API و نبود درگاه عمومی پروکسی نیز بررسی
شود. پاسخ‌دادن پروکسی به‌تنهایی اثبات جمع‌آوری نیست. کلید خصوصی، بستهٔ گواهی،
دایرکتوری زمان اجرا و گزارش پالایش‌نشده در Git یا پیام پشتیبانی قرار نمی‌گیرند.

## درخواست‌های مجاز و ممنوع

آداپتور و پروکسی فقط مسیرهای GET مشخص را می‌پذیرند: اطلاعات و نسخهٔ Engine،
فهرست container/image/network/volume، inspect یک container مشخص، آمار محدود،
گزارش تاریخی محدود و رویداد تاریخی محدود. `HEAD /_ping` برای مذاکرهٔ نسخهٔ SDK
مجاز است. نسخه‌ها به `1.40` تا `1.56` محدودند. پرس‌وجوی هر مسیر ثابت و محدود است؛
tail گزارش بیش از ۲۰۰ نیست. stream/follow، پارامتر تکراری، مسیر کدگذاری‌شده،
خروج از مسیر، upgrade و بدنهٔ درخواست رد می‌شوند.

درخواست‌های `POST`، `PUT`، `PATCH` و `DELETE`، خواندن archive/export، attach،
exec، build، login، Secret، config و عبور دلخواه API مجاز نیستند. تست واقعی،
خود پروکسی را مستقیم می‌سنجد تا محدودیت آداپتور پروکسی باز را پنهان نکند.
پروکسی از راه سوکت هنوز اختیار daemon دارد؛ تنظیم، شبکهٔ خصوصی و سیاست اعتماد
صادرکنندهٔ کلاینت آن مانند دارایی حساس میزبان محافظت شوند.

## دادهٔ امن و مجوز جزئی

شناسهٔ Engine، پروژه و سرویس Compose، container، image، network و volume میان
جمع‌آوری‌ها ثابت می‌ماند. بخش کامل و خالی می‌تواند منابع حذف‌شده را بازنشسته کند.
منع فهرست اختیاری، دادهٔ مجاز بخش‌های دیگر را نگه می‌دارد و وضعیت همان بخش را
صریح ثبت می‌کند. بخش ناقص یا ممنوع، شناسهٔ دیده‌نشده را حذف نمی‌کند. inspect
ناموجود یا ممنوع، شناسهٔ موجود در فهرست را با سلامت نامعلوم و جزئیات ناقص نگه
می‌دارد.

نسخهٔ Engine، حالت و سلامت container، شمار restart، زمان واقعی شروع، کد خروج
container متوقف، مرجع image، شمارهٔ درگاه داخلی و منتشرشده، مقصد mount داخل
container و سقف CPU/حافظه در صورت وجود، مشخصات محدود و معتبر دارند. IP میزبان،
مسیر مبدأ mount میزبان، مقدار محیطی، پاسخ خام inspect و برچسب دلخواه ذخیره یا
برگردانده نمی‌شود. درگاه و mount هر کدام حداکثر ۶۴ و برچسب حداکثر ۱۶ است؛
بیش‌بودن، جزئیات را ناقص می‌کند.

فقط برچسب‌های `com.docker.compose.project`، `com.docker.compose.service` و
`stackplore.io/depends-on` حفظ می‌شوند. نام پروژه و سرویس با حرف یا رقم ASCII
شروع می‌شود و سپس فقط حرف، رقم، نقطه، زیرخط یا خط تیره دارد؛ حداکثر ۱۲۸ نویسه.
وابستگی، فهرست ویرگول‌جدا با حداکثر ۳۲ نام سرویس از همین دستور زبان و ورودی
حداکثر ۴۰۹۶ بایت است؛ فاصلهٔ اطراف حذف، تکرار حذف و ترتیب ثابت می‌شود. فقط
سرویس‌های موجود در همان پروژه به هم وصل می‌شوند. مقدار محیطی خوانده و سرویس
ناموجود ساخته نمی‌شود. مقدار عمومی برچسب وابستگی فقط تا ۲۵۶ بایت حفظ می‌شود.
ورود فایل Compose بی‌اثر اختیاری است و این پروفایل آن را پیاده نکرده است.

## مرز آمار، گزارش و رویداد

CPU با دو نمونهٔ daemon و `IncludePreviousSample=true` محاسبه می‌شود. زمان
نمونه از خود daemon است. نبود نمونهٔ قبلی یا بازنشانی شمارنده، CPU را ناموجود
می‌کند؛ پاسخ خالی صفر مصرف نمی‌سازد. سنجه‌های معتبر دیگر با نبود CPU باقی
می‌مانند. هم‌زمانی آمار و inspect، درخواست، اتصال، بدنه و خاموش‌شدن محدودند.
ساخت زمان اجرا هشت worker، سقف هشت MiB برای هر پاسخ و بودجهٔ مشترک ۳۲ MiB
دادهٔ ورودی برای هر مشاهده دارد. رسیدن به بودجه، پوشش را ناقص نگه می‌دارد.
حداکثر موجودی نرمال‌شده ۱۰هزار مورد است.

گزارش بازهٔ UTC ثابت، tail حداکثر ۲۰۰ خط و بودجهٔ مشترک بایت روی همهٔ containerها
دارد. خروجی بدون TTY جریان stdout/stderr را حفظ می‌کند؛ با TTY نام جریان
«نامعلوم» است. پالایش دادهٔ حساس و سقف هر خط برقرار است. بریدگی بایت یا خط حتی
اگر قاب نخست هیچ خط قابل‌نمایشی ندهد، ناقص گزارش می‌شود. صفحه‌های بعد همان tail
ثابت را می‌خوانند؛ چرخش گزارش در daemon هنوز می‌تواند دادهٔ قدیمی را حذف کند.
گزارش نمونهٔ قبلی Docker پشتیبانی نمی‌شود. نام container در درخواست باید با
هدف inspect‌شده بخواند.

daemon فقط ۲۵۶ رویداد آخر را نگه می‌دارد. جمع‌آور حلقهٔ بدون فیلتر را با
`since=0` و `until` محدود در گذشته می‌خواند؛ نوع مجاز و بازهٔ دقیق در خود
آداپتور انتخاب می‌شوند. فقط اگر قدیمی‌ترین رویداد حفظ‌شده به ابتدای بازه برسد و
API مذاکره‌شده حداقل `1.46` باشد پوشش کامل است. تاریخچهٔ خالی، ابتدای زودتر،
زمان نامعتبر و رسیدن به سقف، پوشش ناقص دارند. خواندن دوره‌ای رویداد ازدست‌رفته
از حلقه را برنمی‌گرداند. پوشش ناقص، بازهٔ کامل هشدار را ثابت نمی‌کند.
[منبع تاریخچهٔ Engine](https://github.com/moby/moby/blob/v28.5.2/daemon/events/events.go)،
[منبع API رویداد](https://github.com/moby/moby/blob/v28.5.2/api/server/router/system/system_routes.go).

## تعویض گواهی

فایل‌ها در شروع فرایند خوانده می‌شوند. فایل را اتمی جایگزین و API یا پروکسی
مربوط را دوباره اجرا کنید تا گواهی تازه خوانده و اتصال قدیمی بسته شود. فعال و
غیرفعال‌کردن منبع به معنی بارگیری دوبارهٔ گواهی نیست.

برای تعویض صادرکننده، ابتدا CA قدیم و جدید را با هم در سمت تأییدکننده نصب و
همان سمت را دوباره اجرا کنید. گواهی و زنجیره و کلید جداگانهٔ سرور یا کلاینت را
عوض، آن سمت را دوباره اجرا و جمع‌آوری احرازشدهٔ واقعی را بررسی کنید. پس از
مهاجرت همهٔ هویت‌های فعال، CA بازنشسته را حذف و دوباره اجرا و بررسی کنید.
اعتماد صادرکنندهٔ کلاینت و سرور دو سیاست جدا هستند. مادهٔ بازگشت تا پاس‌شدن
مسیر تازه خصوصی بماند؛ سپس اعتبارنامهٔ قدیم طبق سیاست کلید اپراتور حذف شود.

## تکرار اثبات

فقط روی میزبان لینوکس موقت با Docker Engine و ابزار Go پین‌شده:

```sh
GOMAXPROCS=2 STACKPLORE_TEST_DOCKER_ENGINE=1 go -C apps/api test -p=2 ./internal/provider/docker -run TestRestrictedProxyOnRealDockerEngine -count=1 -timeout=9m -v
```

تست، تصویر ثابت و بدون shell می‌سازد، container/network/volume با نام و برچسب
یکتا می‌سازد، TLS تست خصوصی و کوتاه‌عمر تولید می‌کند و فقط منابع خودش را پاک
می‌کند. موجودی، وابستگی Compose، سلامت، CPU دو نمونه، حافظه، شبکه، گزارش با و
بدون TTY، رویداد، منع mTLS و مسیرهای ممنوع مستقیم بررسی می‌شوند؛ نسخهٔ هدف پس
از تلاش نوشتن نباید عوض شود. نشان موفقیت
`REAL_DOCKER_RESTRICTED_MTLS_SDK_INVENTORY_STATS_LOGS_EVENTS_AND_DENIALS_PASS`
است. پروکسی fixture با UID مالک فایل تست و گروه‌های فعلی دسترسی سوکت اجرا
می‌شود؛ مجوز کلید تولیدشده `0600` می‌ماند. پروفایل Compose از UID/GID برابر
65532 و گروه سوکت انتخاب‌شدهٔ اپراتور با فایل‌های خصوصی جدا استفاده می‌کند.
این ساخت fixture را به daemon مشتری وصل نکنید. پیش از اجرای برنامه نام‌های
محیطی مخصوص تست را بردارید. پس از پاس، کامیت دقیق، نسخهٔ Engine و نتیجهٔ CI در
سند شواهد ثبت شوند.
