# ارتقا و برگشت

دادهٔ SQLite نسخه‌های قدیمی توسعه، ورودی پشتیبانی‌شدهٔ runtime نیست. PostgreSQL
تنها پایگاه پشتیبانی‌شده است. هر migration جلو می‌رود؛ اجرای binary قدیمی روی
schema جدید برگشت امن نیست.

## از ۱٫۰٫۱ به نامزد اصلاحی ۱٫۰٫۲

نامزد فعلی ledger را از **۱۶ به ۱۷** می‌برد. migration ۱۷، indexهای ترتیب
بایتی اعلان و قانون هشدار را می‌افزاید؛ شرط ادامه و مرتب‌سازی حتی زیر collation
غیربایتی پیش‌فرض هم یک ترتیب دارند. شناسه، مجوز و بایت شانزده migration قبلی
عوض نمی‌شوند. تست واقعی PostgreSQL ارتقا از ledgerهای ۱۴ و ۱۶، بقای داده و
صفحه‌بندی یکسان را سنجیده است؛ پذیرش کامل همان منبع در
[شواهد کنونی](../evidence/1.0.2/README.md) می‌آید.

پیش از ارتقای کنترل‌شدهٔ تک‌مالک، backup بومی بررسی‌شده بگیر. زمان index و
شروع را روی کپی بازیابی‌شدهٔ نماینده بسنج. storage نسخهٔ ۱٫۰٫۲، ledger دقیق
۱۷تایی می‌خواهد؛ آرشیو ۱٫۰٫۱ را با ابزار ۱٫۰٫۱ restore و verify کن، آن runtime
را متوقف کن و سپس همان کپی را ارتقا بده. binary قدیمی روی ledger ۱۷ اجرا نکن
و checksum تاریخی را تغییر نده. برگشت، backup بررسی‌شدهٔ پیش از ارتقا می‌خواهد.

### متن رویداد قدیمی و پاسخ به افشا

نسخهٔ قدیمی شاید متن اعتبارنامه را در خلاصهٔ رویداد بومی ذخیره کرده باشد.
نگاشت اصلاح‌شدهٔ پاسخ REST و پیام نخست و بعدی SSE، سیاست پوشاندن استقرار و
سقف ۸۱۹۲ نویسه را روی خلاصهٔ ذخیره‌شده هم اعمال می‌کند. migration ۱۷ فقط index
می‌افزاید؛ ردیف قدیمی یا backup را بازنویسی نمی‌کند. تست محدود پاسخ گذشت؛
پذیرش کامل منبع اصلاح‌شده در [شواهد کنونی](../evidence/1.0.2/README.md) می‌آید.

۱. دسترسی نسخهٔ قدیمیِ در معرض را محدود یا آن را متوقف کن. پیش از بازکردن
دسترسی رویداد و API، نسخه، منبع و گیت‌های وصله را بررسی کن.

۲. افشای واقعی را در مسیر خصوصی اپراتور بررسی کن. اعتبارنامهٔ افشاشده را
عوض کن؛ ردیف حساس، گزارش ارائه‌دهنده یا دانلود قبلی را در گزارش کار نگذار.

۳. پایگاه باقی‌مانده، آرشیو بومی و خروجی قدیمی را طبق سیاست دسترسی، رمزگذاری
و بایگانی اپراتور محافظت کن. پوشاندن پاسخ، بایت ذخیره‌شدهٔ آن‌ها را عوض نمی‌کند.

۴. اگر انقضا لازم است، [پاک‌سازی محدود و تأییدشدهٔ تاریخچه](../settings.fa.md#پاکسازی-محدود-تاریخچه)
را به کار ببر. پیش‌نمایش دقیق، احراز تازهٔ مخصوص این کار، تأیید یک‌بارمصرف و
پذیرش هشدار backup لازم است. هر بار حداکثر ۱۰۰۰ ردیف واجد شرط پیش از مرز فعلی
نگهداری حذف می‌شود؛ ردیف جوان‌تر می‌ماند. حذف، WAL و backup یا رسانهٔ فیزیکی
را پاک‌سازی امن نمی‌کند. سابقهٔ ممیزی محافظت‌شده را نگه دار؛ حذف سراسری SQL یا
بازنویسی نامحدود هنگام ارتقا اجرا نکن.

## کف وصلهٔ PostgreSQL 17

Stackplore 1.0.x برای سرور و ابزارهای بومی (`psql`، `pg_dump`، `pg_restore`)
به **17.11 یا وصلهٔ جدیدتر از شاخهٔ 17.x** نیاز دارد. نسخهٔ 17.6 پایین‌تر از کف
امنیتی پشتیبانی‌شده است. [فهرست امنیتی رسمی PostgreSQL 17](https://www.postgresql.org/support/security/17/)
را مرور کن؛ ارتقای سرور به‌تنهایی، ایراد ابزارهای کارخواه را رفع نمی‌کند.

طبق [یادداشت رسمی 17.11](https://www.postgresql.org/docs/17/release-17-11.html)،
برای پایگاه موجود 17.x، dump/restore لازم نیست. این حکم، گیت‌های اپراتور را حذف
نمی‌کند:

1. با ابزارهای وصله‌شده، backup بومی تازه بگیر و بازیابی آن را در مقصد خالی جدا
   بسنج؛ [راهنمای backup/restore](backup-restore.fa.md) را اجرا کن.
2. زمان نگهداری را هماهنگ کن، API را متوقف کن و یادداشت نسخه‌های میانی را بخوان.
   تنظیم `output_plugin_libraries`، پاک‌سازی دادهٔ آسیب‌دیدهٔ `pgcrypto` و نیاز به
   reindex برای `btree_gist`/`ltree` را در صورت کاربرد بررسی کن. Stackplore این
   افزونه‌های اختیاری یا افزونهٔ سفارشی رمزگشایی منطقی را نمی‌سازد و به کار
   نمی‌برد؛ افزوده‌های اپراتور را جدا بسنج. پایان‌دهندهٔ دادهٔ `COPY FROM STDIN`
   در اسکریپت‌ها را با `psql` وصله‌شده بررسی کن.
3. image تأییدشدهٔ سرور و ابزارهای بومی را ارتقا بده؛ volume پایگاه را نگه دار.
   نسخهٔ دقیق ابزارها و سرور و digest تصویر را ثبت کن. برای گذر از ارتقا، volume
   را حذف نکن.
4. پس از شروع دوباره، readiness پایگاه، سلامت ledger، ورود، خواندن نمونه و بقای
   داده را بسنج. backup بررسی‌شده را برای بازیابی نگه دار؛ خدمت را با سرور یا
   ابزار آسیب‌پذیر 17.6 از سر نگیر.

تست migration برنامه، اثبات ارتقای سرور از 17.6 به 17.11 نیست. پیش از ادعای
تأیید این مسیر، تمرین جداگانهٔ ارتقای وصله روی محیط دورریختنی لازم است؛ رسید دقیق
آن را در [برنامهٔ شواهد](../implementation-plan.md) ثبت کن.

## پیش از ارتقا

1. changelog، migration و تغییر قرارداد نسخهٔ مقصد را بخوان.
2. tag، manifest checksum امضاشده، هویت بسته و منشأ را با
   [راهنمای بررسی انتشار](release.fa.md) بسنج. تعریف گردش‌کار یا اجرای امضای
   دیده‌نشده، مدرک بستهٔ معتبر نیست.
3. نسخهٔ فعلی، وصلهٔ سرور و ابزار PostgreSQL، تنظیمات استقرار و نگهداری runtime key را ثبت
   کن؛ مقدار secret را کپی نکن.
4. backup بومی PostgreSQL بگیر و آن را در DB خالی تازه restore و verify کن.
5. build مقصد را روی نسخهٔ بازیابی‌شده با migration، readiness، ورود، خواندن
   نمونه و لغو session پس از restore بیازما.
6. برای تنها API برنامهٔ rollout هماهنگ کن؛ دو runtime هم‌زمان روی یک DB اجرا
   نکن.

جزئیات migrationهای قدیمی `0.1.0` تا `0.5.0` و checksumها در
[مرجع انگلیسی](upgrade-rollback.md) است. ledger تغییرناپذیر است؛ آن را برای رد
کردن کنترل upgrade ویرایش نکن.

## ledgerهای بعدی و نامزد ۰٫۹٫۰

فایل migrationهای منتشرشدهٔ قبلی، بایت‌به‌بایت ثابت می‌مانند:

| migration | تغییر |
| --- | --- |
| ۱۱ | پوشش بخش‌های موجودی و حصار مجوز فعلی |
| ۱۲ | هویت جداگانهٔ نصب عادی و مهمان |
| ۱۳ | حالت پایدار مرور، قصد و نتیجهٔ عملیات زیرگیت |
| ۱۴ | تنظیمات نسخه‌دار برنامه و سیاست ممیزی محافظت‌شده |
| ۱۵ | اجازهٔ نمایهٔ اپراتوری mountشدهٔ `kubernetes_kubeconfig` |
| ۱۶ | index هم‌خوان خوراک هشدار منبع با ترتیب زمان تغییر و شناسهٔ مبهم |

migrationهای ۱۵ و ۱۶ فقط رو به جلو هستند. نمایهٔ mountشده فقط مرجع منطقی
ذخیره می‌کند؛ محتوای kubeconfig، اعتبارنامه و مسیر انتخابی مرورگر ذخیره نمی‌شود.
index، طرح query را عوض می‌کند؛ هویت هشدار یا مجوز cursor را عوض نمی‌کند.
کار index، زمان راه‌اندازی و قفل را روی نسخهٔ بازیابی‌شدهٔ نماینده بسنج. ابزار
storage سازگار با آرشیو، ledger دقیق آن را بازیابی کند؛ سپس آن runtime را متوقف
و نسخهٔ آزمایشی را رو به جلو ارتقا بده. ابزار تازه، واردکنندهٔ عمومی ledger قدیمی نیست.

## اجرا و بررسی

API قبلی را drain و متوقف کن، نسخهٔ بررسی‌شده را نصب کن و probeها، ورود، کاربران،
قابلیت منبع، خواندن‌های اصلی و ممیزی/اعلان را بررسی کن. volumeهای PostgreSQL و
runtime key را نگه دار. تعریف استقرار قبلی و backup را تا پایان پنجرهٔ برگشت حفظ
کن. Helm rollback یا image قدیمی schema را عقب نمی‌برد.

در `0.7.0` chart یک Go app با UI embedشده نصب می‌کند؛ API یک replica می‌ماند و
Ingress به همان Service می‌رسد. Compose نیز یک application service دارد. مهاجرت
از نسخه‌ای با Nginx جدا باید در محیط آزمایشی و با backup تازه تمرین شود؛ تغییر
chart تنها proof اجرای target نیست.

init غیر root چارت، زیرپوشهٔ خصوصی PVC را آماده و کلید ریشهٔ قدیمیِ معتبر را
اتمی و بدون جایگزینی به آن می‌برد. کلید تکراری مبهم یا فایل ناامن، شروع را
می‌بندد؛ برای گذر از گیت کلید را حذف نکن. جزئیات در [نصب](deployment.fa.md) است.

## برگشت

اگر نسخهٔ تازه با دادهٔ جدید سازگار نیست، برنامه را offline نگه دار. backup پیش
از upgrade را به DB خالی تازه برگردان و با build قدیمی خودش verify کن؛ سپس secret
استقرار را کنترل‌شده عوض کن. نوشته‌های پس از زمان backup از دست می‌روند؛ اثرش را
پیش از cutover بسنج. DB تازه/ناموفق و آرشیو قبلی را در روند اپراتور نگه دار.

Restore همهٔ session و pre-auth را لغو می‌کند؛ کاربر باید دوباره وارد شود.
پاک‌کردن DB یا آرشیو قدیمی بخشی از فرمان برنامه نیست. مدرک هر upgrade/rollback
روی target جدا از تست محلی ثبت می‌شود.
پذیرش نهایی نامزد در [برنامهٔ شواهد](../implementation-plan.md) ثبت می‌شود؛
پذیرش پروژه، مجوز یا اثبات rollout درخواست‌نشدهٔ مشتری نیست. در رخداد امنیتی،
مدرک را نگه دار و [پاسخ به رخداد](incident-response.fa.md) را اجرا کن.
